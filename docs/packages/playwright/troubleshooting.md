The fixture does nothing

`resolveCaptureConfig()` returns `null` when capture is inactive. That is normal
for a direct `playwright test` run. Start the test through:

```bash
stacknext capture --name candidate -- pnpm exec playwright test --workers=1
```

## `CaptureTransportError`

The run is marked active but the environment is invalid. Check that
`STACKNEXT_TEST_RUN_ID` matches `run-<16 hex>`,
`STACKNEXT_COLLECTOR_URL` is a loopback URL and `STACKNEXT_TOKEN` is present.
Do not set these manually; let `stacknext capture` supply them.

## Samples are incomplete

1. Confirm the app was started with StackNext instrumentation. The server must
   have an active OTel provider and the W3C propagator.
2. Check that the browser request URL is loopback or matches `baseURL`.
3. Look at the sample's correlation reason in `stacknext runs show <run-id>` or
   the MCP `stacknext_get_test_run` response.
4. Confirm the app received the request before the probe timeout. Increase
   `STACKNEXT_CAPTURE_TIMEOUT_MS` only when the app is genuinely slow to start.
5. Run with one worker. Parallel workers are not supported for capture.

## A scenario has no baseline match

The scenario identity changed. Prefer a stable `stacknext.scenario` annotation
and keep it unchanged between the baseline and candidate. See
[Fixture](fixture.md).

## The test passes but the run exits 3

Exit 3 means the child command succeeded but the captured telemetry is
incomplete. It is not a pass. Inspect the run status and sample correlation
before comparing.

## Timeouts

- `STACKNEXT_CAPTURE_SETTLE_MS` (default 500) delays the first probe.
- `STACKNEXT_CAPTURE_TIMEOUT_MS` (default 5000) bounds probing.

Very slow development servers may need a larger timeout, but a consistently
missing document trace usually indicates broken instrumentation, not a short
timeout.

## Verify

```bash
stacknext runs list --json
stacknext runs show <run-id> --json
stacknext doctor
```
