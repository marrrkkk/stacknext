Prisma Client

Query events must be enabled when the client is created:

```ts
import { PrismaClient } from '@prisma/client'

const prisma = new PrismaClient({
  log: [{ emit: 'event', level: 'query' }],
})
```

Prisma's default logging does not emit these events.

## Adapter

```ts
import { instrumentPrismaClient } from '@stacknext/prisma'

const stop = instrumentPrismaClient(prisma, {
  databaseSystem: 'postgresql',
})
```

| Option | Required | Default | Notes |
| --- | --- | --- | --- |
| `databaseSystem` | No | `'prisma'` | Use the engine name, for example `sqlite` or `postgresql`. |
| `transport` | No | Process-wide transport | Must expose `enqueueDatabaseQuery`. |
| `onError` | No | none | Receives telemetry failures; they never reach Prisma. |

## Lifecycle

`instrumentPrismaClient` returns a cleanup function. Calling it removes the
listener and clears the idempotency guard. Calling `instrumentPrismaClient`
again for the same client before cleanup returns a no-op cleanup.

Register the adapter once per Prisma client, after the client is created and
before the first request.

## `stacknext.config.json`

```json
{
  "database": { "drizzle": false, "prisma": true }
}
```

`database.prisma` is setup intent used by `stacknext init` and
`stacknext doctor`. It does not attach the listener; the adapter must be called
explicitly.

## Duration

Prisma query events include a duration in milliseconds. StackNext uses it when
it is a finite number, otherwise `durationMs` is `null`. Null is unmeasured, not
zero.

## Privacy

The adapter never reads `event.params`. SQL is redacted and capped. No
configuration option can enable bind-parameter capture.

## Verify

1. Start `stacknext dev` and exercise a Prisma query.
2. Run `stacknext coverage`; database evidence should be observed.
3. Check that the query duration is measured for Prisma.
4. Open the dashboard Database page or use `list_database_queries` through MCP.
