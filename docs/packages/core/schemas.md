StackNext normalizes telemetry into plain JSON before it crosses the loopback
boundary. `@stacknext/core` exports the TypeScript types and Zod schemas used by
the app-side exporter, the collector and regression capture.

## Version constants

```ts
import {
  STACKNEXT_SCHEMA_VERSION,
  STACKNEXT_SDK_VERSION,
} from '@stacknext/core'

STACKNEXT_SCHEMA_VERSION // 1
STACKNEXT_SDK_VERSION // the installed package version
```

`STACKNEXT_SCHEMA_VERSION` versions the ingest envelope. The SDK version is
reported with each connected instance and is compared during regression
environment checks.

## Ingest envelope

`StackNextIngestEnvelope` is the only body accepted by
`POST /__stacknext/v1/ingest`:

```ts
import type { StackNextIngestEnvelope } from '@stacknext/core'

const envelope: StackNextIngestEnvelope = {
  version: 1,
  instance: {
    instanceId: '...',
    serviceName: 'my-app',
    sdkVersion: '<installed-version>',
    runtime: 'nodejs',
  },
  spans: [],
  errors: [],
  databaseQueries: [],
}
```

| Field | Required | Notes |
| --- | --- | --- |
| `version` | Yes | Must be `1`. |
| `instance.instanceId` | Yes | Identifies one app process. |
| `instance.serviceName` | Yes | Used by request and trace summaries. |
| `instance.sdkVersion` | Yes | StackNext package version. |
| `instance.runtime` | Yes | Only `nodejs` is supported. |
| `instance.projectName` | No | From `stacknext.config.json` or the transport. |
| `instance.nextVersion` | No | Next.js version reported by the app. |
| `instance.runtimeVersion` | No | Node.js version, used for environment checks. |
| `spans` | Yes | At most 500 per envelope. |
| `errors` | Yes | At most 25 per envelope. |
| `databaseQueries` | Yes | At most 100 per envelope. |
| `diagnostics` | No | Exporter queue/drop counters. |

An envelope over the per-array limit, over 2 MiB, with an unknown `version`, or
with an invalid field is rejected before it reaches the store.

## Span shape

`StackNextSpanInput` is the wire form. The collector adds `receivedAt` when it
stores the span.

```ts
interface StackNextSpanInput {
  traceId: string
  spanId: string
  parentSpanId?: string
  name: string
  kind: 'internal' | 'server' | 'client' | 'producer' | 'consumer'
  startTime: number
  endTime: number
  durationMs: number
  status: 'unset' | 'ok' | 'error'
  statusMessage?: string
  serviceName: string
  route?: string
  method?: string
  statusCode?: number
  nextSpanType?: string
  nextSpanName?: string
  nextRoute?: string
  nextPage?: string
  nextSegment?: string
  nextRsc?: boolean
  attributes: Record<string, unknown>
  events: StackNextSpanEvent[]
  resource: Record<string, unknown>
}
```

Framework fields come from the documented Next.js span allowlist in
`packages/core/src/framework.ts`. Unknown span types are retained as verbose
evidence rather than mapped to a guessed feature.

## Error shape

`StackNextErrorInput` carries a redacted message and stack plus optional Next.js
context. The collector adds `fingerprint` and `receivedAt` when storing it.

Fields include `id`, `message`, `name`, `stack`, `digest`, `timestamp`,
`route`, `method`, `requestPath`, `routerKind`, `routeType`, `renderSource`,
`renderType`, `traceId`, `spanId` and `attributes`.

Not every runtime provides a span context. When one is missing, the collector
uses route/method plus a 30-second window for correlation and reports the link
as fallback-based.

## Database query shape

`StackNextDatabaseQueryInput` includes:

- `id`, `traceId?`, `spanId?`, `timestamp`;
- `durationMs: number | null` — `null` means unmeasured, never zero;
- `sql` — redacted SQL text;
- `databaseSystem`, `operation?`;
- `success`, `errorMessage?`;
- `source: 'drizzle' | 'prisma' | 'manual'`;
- `attributes`.

Bind parameters are never part of the type and cannot be captured through it.

## Response types

`@stacknext/core` also exports the collector/CLI/MCP response contracts:
`RequestSummary`, `TraceSummary`, `TraceDetail`, `ErrorListItem`,
`DatabaseQueryListItem`, `PageResult`, `HealthResponse`, `OverviewResponse`,
`CoverageReport`, `DiagnosticReport`, `SnapshotSummary`, `SnapshotPayload` and
`ExportResponse`.

These are additive over time. Consumers should tolerate new optional fields and
read `meta.completeness` or response `limitations` before drawing conclusions.

## Validation rules

- External payloads are Zod-validated at the collector boundary.
- Counts are bounded before storage.
- Duration values must be finite and non-negative; unknown durations stay
  `null`.
- Trace and span ids must be valid hexadecimal W3C ids when they are used for
  correlation.
- Redaction runs before enqueueing and again before storage.

See [redaction](redaction) and the collector's
the repository `docs/privacy.md` for the data boundary.
