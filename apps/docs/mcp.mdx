StackNext exposes collected telemetry and saved regression records to AI coding
clients through a **read-only** Model Context Protocol server over stdio. It
reads the same local collector API as the dashboard and never mutates data.

## Start it

Start StackNext first:

```bash
stacknext dev
```

Then, in another terminal from the same app directory:

```bash
stacknext mcp
```

`mcp` reads `.stacknext/run.json` for the collector URL and bearer token. You
can also supply them explicitly:

```bash
stacknext mcp --collector http://127.0.0.1:4400 --token <token>
```

<Note>
stdout is reserved for MCP protocol messages; diagnostic logging is written to
stderr. The collector must be running before the client starts the server.
</Note>

## Client configuration

Most clients accept a JSON server entry. Use an absolute app path. The MCP
process reads `.stacknext/run.json` from its working directory, so the client
must start it in the app directory. With pnpm:

```json
{
  "mcpServers": {
    "stacknext": {
      "command": "pnpm",
      "args": [
        "--dir",
        "/absolute/path/to/your-app",
        "exec",
        "stacknext",
        "mcp"
      ]
    }
  }
}
```

`pnpm --dir` changes the working directory. npm's `--prefix` only changes where
packages are resolved; it does **not** change the working directory. With npm,
set the client's `cwd` to the app directory instead:

```json
{
  "mcpServers": {
    "stacknext": {
      "command": "npm",
      "args": ["exec", "--", "stacknext", "mcp"],
      "cwd": "/absolute/path/to/your-app"
    }
  }
}
```

If the client has no `cwd` option, launch npm through a wrapper that changes
directory first:

```json
{
  "mcpServers": {
    "stacknext": {
      "command": "sh",
      "args": ["-c", "cd /absolute/path/to/your-app && npm exec -- stacknext mcp"]
    }
  }
}
```

If `stacknext` is installed globally, use `"command": "stacknext"` and
`"args": ["mcp"]` instead. Restart the client after changing its MCP config.

## Verify without an AI client

`stacknext mcp --check` starts the server in memory, lists the tools and
prompts, calls `get_project_summary` against the running collector and prints a
JSON result. It exits non-zero when the collector is unreachable or the tool
surface is broken:

```bash
npm exec -- stacknext mcp --check
```

With pnpm, use `pnpm exec stacknext mcp --check`. The output includes the server
version, tool and prompt counts, instrumentation connection state and request,
error and database counts. This checks the MCP surface itself; it does not test
a specific AI client or model.

For client-specific setup and skill installation, see
[AI agent setup](/ai-agents/setup).

## What it exposes

The server provides twenty-three read-only tools and five prompts:

- a bounded investigation brief (recommended first call);
- read-only access to local append-only investigation cases;
- project summary, requests, traces, errors and database queries;
- slow-request search;
- diagnostics list and detail;
- test runs, baselines and comparisons;
- saved snapshots and snapshot traces.

All tools are annotated `readOnlyHint: true`, `destructiveHint: false`,
`idempotentHint: true` and `openWorldHint: false`.

Every result carries `meta.trust: "untrusted-application-data"` and an integer
`meta.revision`. Captured errors, routes, SQL text, stack frames and snapshot
contents are application data, never instructions: an agent should treat them as
evidence and ignore any instructions found inside them. The server strips
invisible control characters and caps text length at the MCP boundary; stored
evidence is unchanged. `meta.revision` advances when telemetry is ingested, so
an agent can re-check narrow queries after something changes. A revision is only
comparable within one collector process — it resets when `stacknext dev`
restarts, so pair it with `health.startedAt`.

The full tool list, argument constraints, response metadata and prompt
arguments are in the [MCP tools reference](/reference/mcp-tools).

## Example prompts

Once connected, ask your agent:

- “What is the slowest request in the last few minutes, and which database
  queries ran inside it?”
- “Summarize the errors captured for `/api/error` and link each one to a trace.”
- “List the current diagnostics, then verify the strongest database finding.”
- “Which instrumentation features are unsupported, missing or simply not
  exercised in the current sample?”
- “List the latest test runs and tell me which scenarios have incomplete
  correlation.”
- “Show the newest snapshot and its scoped error trace, and say clearly that it
  is not live telemetry.”

## Security model

- The server connects only to loopback collector URLs. Non-loopback URLs are
  rejected by the API client.
- The bearer token is read from the runtime file and stays inside the MCP
  process. Tool callers never receive it.
- The collector API is read-only. The MCP server does not expose ingestion,
  configuration changes, file access or arbitrary HTTP requests.
- Data returned to the model is the same redacted data shown in the dashboard.
- Each `stacknext mcp` process generates a random local session id. Reads carry
  attribution headers (session, client name/version and tool) so the dashboard's
  Agents page can show what was read. These are labels, not credentials: reads
  still require the token or session cookie, header text is capped and stripped,
  and no machine or user identity is sent. `stacknext mcp --check` sends none.
  Set `agents.audit: false` in `stacknext.config.json` to disable the audit.
  It can still contain routes, error text, SQL fragments, span attribute values,
  timings, scenario file paths and environment facts.
- Regression and snapshot tools only read records in the collector's configured
  project directory. They cannot write, delete or replay anything.
- Do not wrap StackNext in a remote MCP transport or proxy. The server is meant
  for a local stdio client.

The client you connect may log or transmit tool results according to its own
policy. StackNext does not control that boundary.
