StackNext rebuilds a deterministic diagnostic report from the current sample.
The same report is available in the dashboard, `stacknext diagnose`, JSON
export, the read-only MCP tools and the Agent Skill.

Diagnostics never call a model, run SQL, read source files or change your code.

## The six rules

| Rule | Category | What it observes | Status |
| --- | --- | --- | --- |
| `n-plus-one-queries` | `database` | The same normalized SQL shape repeated within one trace, aggregated by canonical route across traces | `possible` |
| `slow-request` | `performance` | Requests above `slowRequestMs`, grouped by method and route | `observed` |
| `slow-span` | `performance` | A non-root span whose self time crosses its category threshold | `observed` |
| `repeated-external-http` | `http` | The same normalized external endpoint called repeatedly in one trace, aggregated by route | `possible` |
| `error-fingerprint` | `errors` | Single or repeated errors grouped by canonical route and normalized signature | `observed` |
| `server-error-response` | `errors` | A 5xx request root without a correlated non-control-flow error | `observed` |

These are conservative heuristics. They do not prove an ORM bug, a causal
bottleneck, a retry policy problem or a shared error cause. Read the evidence,
verification steps and limitations on each finding.

<Warning>
A finding is evidence, never a confirmed root cause. `possible` means the pattern
is consistent with a problem, `observed` means the evidence was measured
directly, and neither one is a diagnosis you can act on without verifying it in
the trace.
</Warning>

## Read a finding

A finding contains:

- a deterministic `diag-` id for the current sample;
- the rule, category, severity and status;
- the affected route, time window and trace count;
- a fingerprint of the normalized evidence;
- bounded evidence such as slow-span contributors, trace occurrences, error
  occurrences, query shapes or Next.js phases;
- verification steps and limitations;
- a reference to a related trace when one is available.

Statuses mean:

- `possible` — the pattern is consistent with a problem.
- `observed` — the evidence was measured directly.
- `insufficient-evidence` — the sample cannot support a conclusion.

<Info>
Severity is separate from status. A high-severity finding still needs
verification, and a capped report (`maxFindings`) is not a complete inventory.
</Info>

## CLI

```bash
pnpm exec stacknext diagnose
pnpm exec stacknext diagnose --category database
pnpm exec stacknext diagnose --severity warning
pnpm exec stacknext diagnose --trace-id <trace-id>
pnpm exec stacknext diagnose --id <diagnostic-id> --json
```

The report includes the sample window, counts, notes and limitations. A finding
id is deterministic for its evidence but is not a durable database key.

## Dashboard and MCP

The dashboard `/diagnostics` page lists findings and `/diagnostics/:id` shows
one finding with its evidence and related trace.

In MCP clients:

- `stacknext_list_diagnostics` filters by category, severity, status, rule,
  route, trace id, time, query and pagination.
- `stacknext_get_diagnostic` returns one finding plus bounded evidence and a
  related trace reference.

`get_trace` also returns diagnostic references, but they are pointers. Call
`stacknext_get_diagnostic` for the evidence. The MCP server is read-only and
cannot create, acknowledge or delete findings.

## What diagnostics cannot do

- Execute SQL or `EXPLAIN`, inspect source code or recommend indexes.
- Detect long-term anomalies or alert.
- Call an LLM or external service.
- Turn `not-observed` coverage into proof that a feature is broken.
- Establish causality or statistical significance.
